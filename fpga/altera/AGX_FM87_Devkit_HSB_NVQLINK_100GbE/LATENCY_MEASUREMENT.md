## 100GbE Holoscan Sensor Bridge — Latency Measurement Runbook

Step-by-step procedure for running the GPU RoCE loopback demonstration and measuring
end-to-end FPGA PTP round-trip latency on the Agilex™ 7 I-Series Transceiver-SoC Development Kit (4x F-Tile) 100GbE example design.

**Related docs**

- [System example design README](./README.md) — hardware setup, FPGA programming, RTL


---

## What this measures

Latency is the **FPGA PTP round-trip time** on the Sensor Interface (SIF) transmit path,
captured by the on-chip NVQLink instrumentation ILA while the host runs the RoCE loopback
demo.

The measurement uses the same flow described in the
[NVIDIA Holoscan Sensor Bridge latency documentation](https://archive.docs.nvidia.com/holoscan/sensor-bridge/2.6.0/)
and the GPU RoCE loopback example referenced in
[NVIDIA's HSB paper](https://arxiv.org/pdf/2510.25213):

```
A PTP timestamp (A) is embedded inside a packet generated by the RAM player and routed to the host via a SIF Rx port. The packet is looped back from GPU memory and again timestamped (B) at capture on a SIF Tx port. Then Latency is calculated as follows:-

Round-trip latency = PTP timestamp at capture (B) − PTP timestamp at generation (A)
```

This is **not** the same as Holoscan application-level flow tracking. It measures the
hardware datapath through the FPGA SIF tap, independent of host-side operator scheduling.

## Prerequisites

Complete these steps before starting:

1. [Set up the I-Series Transceiver-SoC Development Kit (4x F-Tile) and NVIDIA host](./README.md#hardware-setup).
2. [Program the FPGA](./README.md#programming-the-fpga) with the 100GbE example design
   (`top.sof`).
3. Install the [NVIDIA Holoscan Sensor Bridge SDK](https://archive.docs.nvidia.com/holoscan/sensor-bridge/2.6.0/)
   on the NVIDIA host.
4. Confirm the 100GbE QSFP link is up between the I-Series Transceiver-SoC Development Kit (4x F-Tile) and the host RoCE NIC.
5. Have the ILA capture scripts available on the host:
   - `ila.py` — arms the FPGA ILA and writes `output/samples.csv`
   - `latency_calc.py` — analyzes the capture and writes statistics and plots

## Use two terminals on the NVIDIA host

The RoCE loopback demo **blocks** its terminal while running. Use separate sessions:

| Terminal | Where you work | Purpose |
| --- | --- | --- |
| **Terminal A** | Inside the HSB demo docker container | Start and leave `gpu_roce_loopback.py` running |
| **Terminal B** | Host shell (**outside** docker) | Run `ila.py` and `latency_calc.py` |

Do **not** run the ILA scripts inside the same docker session that is blocked on the
loopback application.

---

## Terminal A — start the demo container and RoCE loopback

On the NVIDIA host:

```bash
cd <holoscan-sensor-bridge>
sh docker/demo.sh
```

If a previous demo container is still present:

```bash
docker ps -a --filter name=demo
docker rm -f demo
```

Wait for the container prompt (example: `root@<host>:<holoscan-sensor-bridge>#`).

Inside the container, start the 100GbE loopback example:

```bash
python3 examples/gpu_roce_loopback.py \
  --hololink 192.168.0.2 \
  --frame-size 32 \
  --mtu 256
```

### Success signals (leave Terminal A running)

You should see messages similar to:

- `DOCA Verbs RoCE Receiver started successfully`
- Hololink / board peer configured (host and FPGA data-plane addresses appear in the log)
- `HoloLink configured successfully`
- Graph running / GPU monitoring loop active

**Leave Terminal A alone** while measurements run.

### Stopping Terminal A

1. Try **Ctrl+C** once or twice inside the container.
2. If the session is frozen, open **Terminal B** on the host and run:

```bash
docker kill demo
```

---

## Terminal B — ILA capture and latency analysis

Keep Terminal B on the **host shell** (not inside docker). With Terminal A's loopback still
running:

```bash
cd ila_scripts

python3 ila.py
# Expect: UDP target to the FPGA Hololink control plane, capture steps,
#         then: Wrote CSV: output/samples.csv

python3 latency_calc.py
# Prints latency statistics and writes plots under output/
```

### Output files

Typical files under `<ila_scripts_directory>/output/`:

| File | Description |
| --- | --- |
| `samples.csv` | Raw ILA capture from `ila.py` |
| `latency_time_series.csv` | Per-frame latency series (µs) |
| `latency_analysis.png` | Summary plot |
| `latency_time_series.png` | Latency vs. sample index |
| `latency_histogram.png` | Distribution histogram |
| `latency_*_p99.*` | P99-filtered variants |

---

## Interpreting results

`latency_calc.py` analyzes capture rows **1024:2048**, removes invalid timestamps, and
excludes the first three valid rows before computing statistics. Compare like metrics
between runs (mean to mean and percentile to the same percentile).

## Possible optimizations
### GUI
If running through the graphical session, make sure any other programs are closed.

### CLI
To minimize resource usage, it is recommended to use SSH. We can try killing unneeded processes and see how it affects the result.


#### GPU applications
The most important optimization is to reduce GPU usage. The GPU should be exclusively used for compute purposes.

To view running processes that are using GPU resources, run the command:

```bash
nvidia-smi
```

Notice that gnome-shell and Xorg are using the GPU. These are part of the GNOME desktop environment.

GNOME Display Manager is responsible for rendering the desktop enviornment. It uses GPU resources that can be reallocated. To kill it, run the commands:

```bash
sudo systemctl stop gdm.service
sudo systemctl stop gnome-remote-desktop.service
```

#### Background processes
A less important optimization, but it could help.

These machines run several processes in the background. Most of them provide ancillary functions for desktop use. Since we are not using the GUI, we can kill these processes.

To view all currently running processes interactively, run:

```
htop
```

To list all currently running background services use:

```bash
systemctl list-units --type=service --state=running --no-legend --no-pager
```

Try stopping some processes that are not necessary:

```
sudo systemctl stop accounts-daemon.service
sudo systemctl stop bluetooth.service
sudo systemctl stop colord.service
sudo systemctl stop kerneloops.service
sudo systemctl stop lpd.service
sudo systemctl stop ModemManager.service
sudo systemctl stop switcheroo-control.service
```

## Troubleshooting

| Symptom | Likely cause | Action |
| --- | --- | --- |
| `docker: container name /demo already in use` | Previous demo still running | `docker rm -f demo`, then retry `sh docker/demo.sh` |
| Loopback starts but ILA capture fails | FPGA not programmed or wrong bitstream | Re-program `top.sof`; confirm Hololink peer in loopback logs |
| No valid samples in `latency_calc.py` | Loopback not running during ILA capture | Ensure Terminal A loopback is active before running `ila.py` |
| Results differ unexpectedly between runs | Wrong analysis window or stale CSV | Re-run `ila.py` then `latency_calc.py`; confirm `samples.csv` timestamp |
| Terminal A frozen; Ctrl+C has no effect | Normal for nested docker + DOCA session | Use Terminal B: `docker kill demo` |
